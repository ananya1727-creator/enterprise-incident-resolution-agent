# Operational Dashboard

Companion to [AGENT_ARCHITECTURE.md](AGENT_ARCHITECTURE.md), [RISK_POLICY.md](RISK_POLICY.md), and [EVALUATION.md](EVALUATION.md). The dashboard is an **operational interface for observing and interacting with the agent** — it contains no incident-resolution logic of its own.

## Run it

```bash
python -m dashboard.server
```

Then open `http://127.0.0.1:5050/`.

## Tech stack decision

Before implementing, the existing project was inspected: pure Python throughout (`agent/`, `mcp_server/`, `scripts/`), no existing frontend, no build tooling, dependencies added so far are `mcp` and `pytest`. Given that:

- **Backend: Flask.** Smallest reasonable choice for a JSON API over existing Python objects — no ORM, no async framework, no unnecessary abstraction. The one place true concurrency is required (a live agent run blocking on human approval while the UI keeps polling) is handled with plain `threading`, not an async framework, since `agent/orchestrator.py` is itself synchronous and rewriting it to be async purely to serve a dashboard would violate "keep the agent logic separate from the UI."
- **Frontend: a single static HTML page + vanilla JavaScript (`fetch`, no framework, no build step).** Five views, all read-mostly with two write actions (launch, approve/reject) — this does not need React/Vue/a bundler. Zero new frontend dependencies; the page is served directly by Flask's `send_from_directory`.
- **No database.** The dashboard has no persistent state of its own — see "Data flow" below.

This keeps the whole addition to two new runtime dependencies (`flask`, already-present `mcp`/`pytest`) and no build pipeline.

## Data flow: no fake data, no duplicated logic

Every view is a projection of real, already-existing agent state or already-generated reports:

| View | Real data source |
|---|---|
| Incident Queue | `data/incidents.json` (fixture incidents not yet run) + `runs/*.json` (every incident ever actually run, by `main.py`, `scripts/run_eval.py`, `scripts/run_benchmark.py`, `scripts/run_e2e_tests.py`, or the dashboard itself) + any incident currently running live in this dashboard process |
| Incident Investigation | The selected incident's `agent.models.IncidentState`, via `agent.orchestrator._state_to_dict` — the exact same serialization the CLI (`main.py`) and observability layer (`agent/observability.py`) already use |
| Human Approval Center | Real, currently-pending `ApprovalRequest` objects from live orchestrator runs — see "Approval bridging" below |
| Analytics | Two **explicitly separate** sections: real metrics computed live from `runs/*.json` + any live incidents, and simulated benchmark metrics read directly from `reports/evaluation_results.json` (generated by `scripts/run_benchmark.py`) |
| Agent Performance | Tool usage/escalation rate/root causes aggregated from every real run trace; resolution accuracy/false remediation rate read from the benchmark report |

`dashboard/data_sources.py` and `dashboard/registry.py` only ever *read* `agent/` state or *launch* a real `Orchestrator` — neither module contains a single hypothesis-scoring rule, tool-selection heuristic, or guardrail check. If a report hasn't been generated yet (`reports/evaluation_results.json` missing), the Analytics/Performance views say so explicitly rather than showing a zero or a guess.

## Approval bridging: approvals genuinely affect execution

This is the part of the dashboard that is not just a read-only viewer. `Orchestrator.approval_callback` (already part of the agent's design, added originally for the adversarial eval harness's default auto-approve) is called **synchronously, on the orchestrator's own thread**, at the exact point (`agent/orchestrator.py::_route_to_approval`) execution must pause for a gated action.

`dashboard/registry.py`'s `DashboardRegistry.launch()` starts each incident's `Orchestrator.run()` in its own background thread and supplies a callback that:

1. Registers the real `ApprovalRequest` in a shared dict, keyed by `approval_request_id`.
2. Blocks that real orchestrator thread on `threading.Event.wait()` — the agent thread is genuinely suspended, mid-execution, not merely "shown as pending" in a UI state.
3. Returns only once `POST /api/approvals/<id>/decide` is called, which sets the decision and the event — the *only* code path that can unblock it.

Verified directly while building this (not just by inspection): launching `INC-0004` produced a real `AWAITING_APPROVAL` state with the orchestrator thread blocked; calling the decide endpoint (both via `curl`/`Invoke-RestMethod` and via an actual click dispatched on the rendered "Approve" button in a browser) caused the same thread to resume, execute `update_adapter_timeout`/`rotate_certificate`, run verification, and reach `RESOLVED` — end to end, through the real agent, not a mock.

## Views

1. **Incident Queue** — incident ID, title (symptom description), severity, criticality, SLA status (OK/At Risk/Breached, computed the same way `IncidentState.sla_remaining_fraction()` does), current agent state, assigned team (from `data/interfaces.json`), resolution status. Clicking a row (or "Launch" for a not-yet-started fixture incident) opens/starts it.
2. **Incident Investigation** — incident details, current state, selected skill(s) (derived from which hypothesis categories actually received evidence, via `agent/skills.py`'s `CATEGORY_TO_SKILL`, same mapping the observability layer uses), evidence collected, hypotheses + confidence, diagnostic tools + results, decisions, actions taken, verification results, escalation status, final resolution, and a merged chronological activity timeline. Decision rationales shown are exactly `DecisionLogEntry.reason` — concise, evidence-cited text the agent already produces; there is no separate chain-of-thought to redact (see `agent/observability.py`'s module docstring for why).
3. **Human Approval Center** — every currently-pending approval, with proposed action, reason, supporting evidence, risk level, and an expected-impact summary (`TOOL_IMPACT_SUMMARY` in `dashboard/server.py`, one line per gated tool, consistent with `docs/TOOL_SPEC.md`). Approve/Reject buttons call the real decide endpoint.
4. **Analytics** — the 12-ish metrics split into a "Real operational metrics" card and a "Simulated benchmark metrics" card, each explicitly labeled with what it is and where it comes from.
5. **Agent Performance** — tool usage (success/fail counts across every real run), escalation rate, most common root causes (all from real run traces), plus resolution accuracy / false remediation rate / tool selection accuracy pulled from the benchmark report and labeled as benchmark-derived.

## What's intentionally out of scope

- No auth/multi-user session model — this is a local operator console, not a hosted multi-tenant product.
- No persistent database — restart the process and only `runs/*.json`-backed history survives (which is the correct behavior: that's the agent's real durable record, not the dashboard's).
- The "Incident Queue" caps the not-yet-launched fixture list at 40 rows (out of 100) to keep the page reasonable; already-tracked incidents are never capped.
